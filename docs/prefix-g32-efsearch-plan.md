# G=32 分级前缀在十种索引规模下的 recall 阈值扫描计划

状态：修订待实施。日期：2026-11-06。本文件定义新版实验协议，不代表已完成新版扫描或取得阈值结果。此前四规模脚本、pilot 和报告属于旧协议，现有脚本必须适配本修订后才能执行。

## 1. 目标与变更边界

固定分级前缀策略 `--read-strategy prefix --prefix-granularity 32`，测量节点数 N=1000、2000、5000、10000、20000、50000、100000、200000、500000、1000000 的索引，分别定位平均 recall@10 为 0.95、0.99 的 efsearch 阈值区间。定义整数停止宽度映射 `W={1000:3,2000:3,5000:3,10000:4,20000:4,50000:4,100000:5,200000:5,500000:5,1000000:6}`；1K/2K/5K 使用相同精度以便对照，10K/20K/50K/100K/200K/500K/1M 对应 `floor(log10(N))`。整数二分至 `|L-R|<=W(N)` 后直接取区间中点，不再逐整数精扫，不再证明精确的最小达标整数。1M 的区间宽度定义为 `R-L`，必须不超过 6。

**严格沿用当前搜索语义，不实现标准 HNSW 搜索，不新增搜索模式开关。** 后续实现只能修改、复用或新增 `scripts/` 下的脚本；不得修改 C++ 源码、头文件、测试、CMake 或第三方代码。本计划及最终实验报告是 `docs/` 下的文档产物，生成的数据、索引和结果不属于源码修改。

单点预估超过 30 分钟必须后台运行，原始数据统一输出到仓库相对路径 `out/prefix_g32_efsearch`；十规模二十个目标均结束后再统一分析和生成报告。允许按规模分批执行并发布各自的 `N{N}_DONE.json`，但不得将局部完成标记当作全部完成。

## 2. efsearch 的实际含义

依据 [QueryEngine::search](../src/runtime/query_engine.cc)：

- `expanded < ef_search_` 限制每查询成功扩展的非删除节点数；frontier 提前为空时，实际扩展数可以小于 efsearch，不是恒等于 efsearch。
- 读取邻居向量以计算候选距离不计入 expanded；同一未扩展节点还可能被重复读取或重复入队。因此 efsearch 不是向量读取数、距离计算数或 RDMA READ 次数的上限。
- 当前实现将每个节点的所有有效层邻居放入同一 frontier，没有标准 HNSW 的高层贪心下降和 L0 束宽搜索，也没有按结果集最差距离剪枝。
- `best` 仅保留已扩展节点，并最终返回其中最近的 k 个；efsearch 同时作为 best 的容量，但不能据此将它解释为标准候选集束宽。

所有产物标注 `search_semantics=prototype_expansion_budget`，横轴写作“efsearch（扩展节点预算）”。本实验的 efsearch 数值不能直接与标准 hnswlib 的 ef 对比。

[历史 100K 报告](prefix-rdma-100k-report.md)中的 efsearch=64、recall=0.0447 仅作历史记录，不能线性外推 0.95/0.99 的阈值；其 GT 必须经过本计划第 4 节核验后才能用于质量对照。

## 4. 数据、索引与真值门禁

### 4.1 十规模数据与索引

复用 `build/dump_vectors` 和 `build/hnsw_build`，脚本负责调用，不修改生成器或构图实现。

1. 导出 seed=42 的 1M base，按完整 fvecs 记录截取前 1K/2K/5K/10K/20K/50K/100K/200K/500K，保留节点 ID 为行号。复用已有小规模输入时，须逐记录核验其与 1M base 的对应前缀一致，不能仅凭相同 seed 或文件名推断一致。
2. 为每个规模使用对应 base 独立构图。不能截断 1M 索引文件来获得小索引，也不能只限制搜索时可见的节点数。
3. 可核验后复用现有各规模索引；必须确认其实际 N、维度、M、向量与构图来源。文件名不能证明 ef_construction 或 seed；来源无法确认时，在本实验独立目录重建，禁止覆盖历史索引。
4. 查询复用 `data/prefix100k/query_quality.fvecs` 前先验证维度、1000 条记录、seed=45 的生成来源及 SHA-256。来源无法确认时由现有生成器重新导出到独立目录。禁止使用 base 的生成种子临时生成查询。
5. 每个规模保存 base、索引、query、GT 的 SHA-256；实验前后检查索引哈希不变。

### 4.2 必须先修正并验证 GT 读取

旧版 [compute_gt.py](../scripts/compute_gt.py) 的 `read_fvecs()` 曾将文件按 int32 读取后，对向量数据调用 `astype(np.float32)`，把浮点位模式对应的整数转换成浮点数，而不是还原原始 float32 向量，可能生成错误真值。前一轮已修正脚本，新实验仍须通过以下门禁。

维度头按小端 int32 解码，向量载荷按小端 float32 解释，并逐记录验证维度、文件长度、有限值及 base/query 维度一致。十规模各自计算并验证 GT，不默认信任既有 `gt_quality_k10.u32`。已有输入和已修正 GT 仅在来源、哈希及抽检全部通过后允许复用；来源未核验的规模必须独立构图和计算 GT。

便宜的反证检查：脚本解析结果的前几行必须与按 fvecs 记录直接解包的 float32 值一致，合成数据各维应在 [-1,1]。若出现巨大整数数量级，停止计算。

### 4.3 精确 top-10

对每个 N 单独使用该规模 base 计算精确 L2 top-10；不能从 1M top-10 中过滤 ID 来代替小规模 GT。输出沿用驱动支持的无头、小端 uint32 行优先格式，1000 x 10 x 4=40000 字节。

GT 建议以 float64 分块计算距离，控制内存占用；固定距离相同时按节点 ID 排序。每个规模至少对固定的 10 条查询用独立的直接差平方求和方式重算，验证 top-10、ID 范围和无重复 ID。若第 10/11 名出现距离并列，记录并列情况，避免将等距近邻替换误判为搜索回退。

正式查询使用 `--queries FILE --gt FILE`，不传 `--base`，避免驱动在线暴力搜索改变运行成本。驱动可能对缺失 GT 行跳过质量计算，脚本必须严格检查 GT 行数与查询行数一致。

## 5. 扫描与阈值定位

### 5.1 指标定义

对 Q=1000 条查询，GT_N(q) 是该规模精确 top-10，A_N,e(q) 是当前原型在预算 e 下返回的结果：

```text
recall@10(N,e) = sum_q |A_N,e(q) intersect GT_N(q)| / (Q * 10)
ef_target(N,t) = min {e in integers, 10 <= e <= N: recall@10(N,e) >= t}
t in {0.95, 0.99}

recall@10(N,L) < t <= recall@10(N,R)
W(1000) = 3; W(2000) = 3; W(5000) = 3; W(10000) = 4; W(20000) = 4; W(50000) = 4; W(100000) = 5; W(200000) = 5; W(500000) = 5; W(1000000) = 6
R - L <= W(N)
ef_estimate(N,t) = floor((L + R) / 2)
```

`ef_target` 是理论上的最小达标整数；本轮交付的是最终实测夹逼区间 `(L,R]` 与中点 `ef_estimate`。在非降假设成立时，中点与区间内真实阈值的整数偏差至多为 `ceil(W(N)/2)`，十规模分别为 2、2、2、2、2、2、3、3、3、3。中点不保证 recall 达标，不得将其标注为“最小达标 ef”或“保证达到目标的预算”；保证达标的实测参考值另列为 R。若 ef=10 已达标，直接报告 10，不构造 ef=9 的下界。实现使用整数映射 `{1000: 3, 2000: 3, 5000: 3, 10000: 4, 20000: 4, 50000: 4, 100000: 5, 200000: 5, 500000: 5, 1000000: 6}`，避免浮点对数取整造成误差。

目标是全查询集平均 recall，不是“95%/99% 的查询全部命中”。比较使用原始数值，不根据图上四舍五入后的 0.95/0.99 判断。1000 条查询对应 10000 个 GT 位置，平均 recall 的离散步长为 0.0001；可将摘要 recall 恢复为最邻近的整数命中数，并检查误差，分别与 9500/9900 比较。

### 5.2 小样本耗时标定

先对十规模各用固定前 20 条查询和对应 GT，运行去重后的 `min(64,N)、min(256,N)、min(1024,N)、min(4096,N)`，估计大 ef 的时间及内存。pilot 结果单独存放，不并入 1000 查询实测点，也不用于最终阈值。

对每个待执行点，以 pilot 和已完成正式点估算完整 1000 查询耗时，记录估算方法、样本、预测秒数及更新时间。可采用已测最大“每查询每扩展预算耗时”线性外推并乘 1.5 安全系数；这不是运行时上限。

预测大于 1800 秒时必须后台运行，不再因超过 30 分钟而停止实验，也不能将正式点改为少量查询。推荐编排器整体脱离终端运行，顺序等待每个客户端结束，避免后台切换丢失二分状态。预测不可靠时同样按后台任务处理。单点超时独立设置为至少 `max(3600, 3*预测秒数)`，写入任务元数据；不沿用旧脚本固定 1800 秒超时或一小时估算总量门禁。记录内存、磁盘余量，资源不足或真实超时仍须明确失败，不自动降配。

### 5.3 按需寻找目标区间

每个规模使用以下去重、排序、裁剪到 [10,N] 的预算序列寻找目标区间：

```text
10, 16, 32, 64, 128, 256, 512, 1024, 2048,
4096, 8192, 16384, 32768, 65536, 131072, 262144, 524288, N
```

每点固定 1000 查询。从小到大执行，两个目标共享实测点；一旦两个目标均找到低于目标的 L 和达到目标的 R，即停止继续增大粗扫预算，进入二分，不要求完成全曲线或强制测到 N。若 ef=10 已达到某目标，直接确定该目标为 10。只有某目标一直未达标时才继续至 N；ef=N 仍未达标，才能给出该目标未达标结论。这样只为二十个目标寻找必要证据，不再要求完整粗扫矩阵。

2K/5K 先实测 ef=10 和 1K 的边界/中点 ef=46、47、48、78、79、80，分别对照 1K 的 0.95 区间 `(46,48]`、中点 47，以及 0.99 区间 `(78,80]`、中点 79。对照点使用各规模自己的索引和 GT，标记用途 `reference_n1000`；不能沿用 1K 的 recall 或按 N 比例外推。对照点若已夹住目标，直接二分；否则按上述序列补充必要点，直至夹住目标或达到 N。记录 1K 来源 campaign 和输入哈希，核验查询一致、base 前缀一致；已有点不重复运行。

### 5.4 二分定位与中点估计

1. 对每个目标，从全部已有正式点中取相邻的夹逼端点 L、R，满足 `recall(L)<t<=recall(R)`。若 ef=10 已达标，则阈值直接为 10。
2. 当前代码的扩展顺序不依赖 efsearch，best 也不参与 frontier 决策；固定图、查询及无边界等距替换时，扩大预算应保留已有命中，因而预期 recall 非降。先检查所有已测点；不能把非降当作无需验证的普遍 ANN 定理。
3. 当 `R-L>W(N)` 时，取 `M=floor((L+R)/2)`，运行完整 1000 查询；若 `recall(M)>=t` 则令 R=M，否则 L=M。每次更新立即原子保存区间和下一个任务，两个目标复用已完成点。
4. 首次满足 `R-L<=W(N)` 时立即停止二分，固定该区间并直接取 `ef_estimate=floor((L+R)/2)`。N=1000/2000/5000/10000/20000/50000/100000/200000/500000/1000000 的 W 分别为 3/3/3/4/4/4/5/5/5/6。若中点尚未测过，只额外运行这个中点以记录真实 recall，不再据此继续二分，不扫描区间其他整数，也不要求 e-1 或三次重复确认。中点即使低于目标，也保留原中点估计并明确标注，不擅自改取 R。
5. 如出现非单调、额外复现不一致或等距边界异常，停止该规模的二分，核验输入、GT、进程和数值精度。无法排除异常时报告 `invalid_nonmonotonic` 或 `blocked`，保留原始证据，不声称区间保证或精确最小值；其他规模可继续独立执行。

二分次数随实际区间而变，不预先承诺固定总运行数。中点是区间估计，不是插值预测 recall；必须分开保存区间、估计值、中点实测 recall 和中点是否达标。

### 5.5 未达标和中断

- ef=N 仍未达目标：报告“在当前图及搜索可达范围内，ef<=N 未达标”，附最大实测 recall。预算 N 足以耗尽可扩展节点，但不保证图中所有节点从入口可达，不能预设 recall=1。
- 尚未运行到 N 或发生超时：报告“预算内未找到，尚不能判断是否可达”，附最大已完成 ef 与 recall；不能写作算法不可达。
- 单点超时、读取错误、GT 不合法、索引变化或进程异常不能按 recall=0 入表，也不能静默跳过。

## 6. 脚本实施方案

复用既有三个 Python 脚本并适配新版协议，不新增 C++ 功能。下列新版后台、状态和目录接口属于待实现要求，不能假设现有脚本已经支持。输入准备、运行时门禁和区间更新在扫描过程中进行；跨规模合并、绘图和正式报告只在全部任务结束后统一执行。

| 脚本 | 工作 |
| --- | --- |
| `scripts/compute_gt.py` | 修正 fvecs 解码，补校验及精确 GT 自检；仅在脚本内修改 |
| `scripts/run_prefix_g32_efsearch.py` | 十规模输入、pilot、1K 边界对照、按需括区间、按 N 二分到宽度 3/3/3/4/4/4/5/5/5/6、中点实测、后台执行、进程状态、超时与续跑 |
| `scripts/analyze_prefix_g32_efsearch.py` | 全部结束后核验原始数据、合并已测点、输出二十项目标的区间/中点/达标情况、绘图和报告 |

编排脚本调用 `build/baseline1_experiment`，单点参数模板：

```bash
./build/baseline1_experiment --transport mmap \
  --index "$INDEX" --queries "$QUERY_FILE" --gt "$GT_FILE" \
  --read-strategy prefix --prefix-granularity 32 \
  --ef-search "$EF" --k 10 --cache-capacity 100000 --warmup 0 \
  --ef-construction 200 --seed 42 --dataset synthetic \
  --workload query --label "n${N}_g32_ef${EF}_r${REP}" \
  --out "$PER_QUERY" --summary-out "$SUMMARY"
```

复用 [run_prefix_sweep.sh](../scripts/run_prefix_sweep.sh) 的驱动参数组织与 [run_rdma_prefix_100k.sh](../scripts/run_rdma_prefix_100k.sh) 的独立运行目录思想，不直接套用其写死 N 的标签、多策略矩阵、自动清空结果或仅凭文件非空跳过的逻辑。

每次运行写入临时目录，退出码为 0 且数据校验通过后才原子发布完成标记。续跑键包含 N、ef、repeat、G、k、语义、transport、缓存参数，以及索引/query/GT/可执行文件哈希；仅存在 CSV 不表示完成。修改脚本版本或关键输入后禁止误复用旧结果。

新版另加 `protocol_version=g32_threshold_midpoint_v2`、查询数、停止宽度映射和输入来源身份；不复用旧协议的完成标记。停止宽度映射纳入 manifest、续跑身份及每个目标的状态文件，禁止误用旧宽度 10 的终态。经核验的旧输入可以复用，但新结果必须进入新 campaign。编排器对 campaign 加独占锁，防止人工重复启动导致并发写同一点。一个 N/ef 只启动一个客户端；跨规模默认也串行，避免内存争用影响估时。

### 6.1 后台进程与退出协议

编排任务通过 `nohup` 加 `setsid`，或机器上可用的持久化任务管理服务启动，脱离 SSH/编辑器终端；标准输入重定向自 `/dev/null`，stdout/stderr 写 campaign 日志。不能仅依赖交互终端的 `&`。大于 30 分钟的单点由该后台编排器启动和等待，不需要让同一点重复后台化。

启动时保存控制进程 PID、进程组 PGID、主机名、系统 boot ID、`/proc/<pid>/stat` 的 starttime、启动时间和完整命令；每个客户端也记录 PID、身份和开始/结束时间。使用独立监护进程维护 `heartbeat.json`，至少每 60 秒更新一次，不能因同步等待客户端而停止心跳。

**后台启动成功后，启动端必须立即向用户输出预计完成时间，不能仅写日志。** 输出至少包含 campaign 绝对路径、控制进程 PID、当前点 N/ef、当前点预计剩余时长与完成时间、整个实验（含最终统一分析）预计剩余时长与完成时间，以及状态检查文件路径。完成时间使用带 UTC 偏移的 ISO 8601 时间，同时显示时区名，避免用户误读日期或跨日时间；后台启动未确认成功时不得输出“已启动”。

预计完成时间按“估算时刻 + 剩余工作耗时”计算，不把已消耗时长重复累计。全实验估时须包含尚未完成的规模、目标括区间、二分、中点实测和最终分析；共享 N/ef 点只计一次。未来二分点未知时，依据当前区间、最多所需二分次数和 pilot 成本模型给出估算范围，并明确为预测而非保证，不得把当前单点完成时间当作整个实验结束时间。pilot 尚未完成或估时依据不足时，立即输出“后台已启动，预计完成时间待 pilot 标定”，待可估算后补充实际时间；不可虚构精确时间。

将 `estimated_at`、`estimated_remaining_seconds`、`estimated_finish_at`、全实验预计完成时间范围、估算依据及覆盖范围写入 `status.json`，单点估时同时写入 `task.json`。每完成一个点、更新二分区间或发现实际耗时显著偏离预测后重新估算，更新状态与日志；若启动端已返回，则人工可通过 `status.json` 获取最新预计完成时间。最终报告保留初始预测与实际完成时间，便于核验误差。

`status.json` 原子更新 `state=preparing|running|completed|failed|interrupted`、当前 N/ef/目标、已完成点数、二十个目标状态、待运行点、最后进展时间及错误。单点失败有明确退出码；超时、信号退出及异常均不发布完成标记。失败点可重试但必须保留各次尝试日志。

编排结束时先确认全部子进程已回收，再写 `exit.json`（退出码、原因、结束时间）。只有十规模二十个目标都有完整合法的区间/中点证据，或有实测 ef=N 未达标证据时，才以退出码 0 原子发布 `SCAN_DONE.json`。单独完成某规模只发布 `N{N}_DONE.json`。仍有失败、非单调、缺点或中断时写 `SCAN_FAILED.json`，不得伪装为完成；被 SIGKILL 或主机重启导致来不及写标记的任务由人工检查判为异常中断。

扫描成功后自动调用分析器一次，或由人工核验成功后手动调用；分析成功才发布 `ANALYSIS_DONE.json`。扫描期间不生成最终阈值报告。失败 campaign 可统一生成故障清单，但不能发布成功分析标记。

### 7.1 人工核验是否结束

以下命令用于后续实现上述文件协议后检查，不是当前脚本已有的状态接口。先将 `CAMPAIGN` 设置为本次启动时打印并记录的真实绝对路径：

```bash
CAMPAIGN=/home/jtz/RDMA-HNSW-Lab/out/prefix_g32_efsearch/campaign_实际时间_实际哈希
python -m json.tool "$CAMPAIGN/controller.json"
python -m json.tool "$CAMPAIGN/status.json"
python -m json.tool "$CAMPAIGN/heartbeat.json"
tail -n 30 "$CAMPAIGN/controller.log"
```

从 controller.json 读取 PID 和 PGID，人工替换下面数值；在记录的同一主机执行：

```bash
PID=实际控制进程PID
PGID=实际进程组PGID
ps -p "$PID" -o pid,ppid,pgid,lstart,etime,stat,args
ps -eo pid,ppid,pgid,etime,stat,args | awk -v group="$PGID" 'NR==1 || $3==group'
cat /proc/sys/kernel/random/boot_id
```

PID 存在时，还须比对命令、记录的 boot ID 和 `/proc/<pid>/stat` 第 22 字段 starttime，避免 PID 被复用；解析 stat 时必须正确处理括号内进程名，不能简单按空格切整行。控制进程不在但进程组仍有客户端时是孤儿任务，不算完成，先排查。`kill -0` 成功、日志暂时不增长或 CSV 已出现均不能单独证明状态。

人工判定规则：

1. **仍在运行**：控制进程身份匹配，当前客户端身份合理，心跳持续更新。心跳超过 180 秒未更新时标记待排查，不能直接认定任务结束或重复启动。
2. **扫描成功结束**：控制进程与所属客户端均已退出；`exit.json` 退出码为 0，`status.json` 为 completed，存在 `SCAN_DONE.json`，二十个目标都有合法终态和关联完成证据。读取该标记及任务清单检查，不凭文件个数猜测成功。
3. **全部处理完成**：在扫描成功基础上，存在 `ANALYSIS_DONE.json`，其中记录 analysis 退出码 0、输入清单身份和报告/CSV/图片哈希；分析器进程也已退出。只有此时对外声明“全部完成”。
4. **异常结束**：进程不在但缺少成功标记，或退出码非零、存在 `SCAN_FAILED.json`、目标状态缺失/失败，应判为失败或中断。保留目录，核验后在同一 campaign 续跑，不把“没有进程”解释为实验成功。

可在检查时查看两个退出与完成文件：

```bash
python -m json.tool "$CAMPAIGN/exit.json"
python -m json.tool "$CAMPAIGN/SCAN_DONE.json"
python -m json.tool "$CAMPAIGN/ANALYSIS_DONE.json"
```

文件缺失本身是需要进一步结合进程状态判断的证据，不应通过预先创建空标记消除报错。

## 9. 20K / 50K 五组构图种子的 recall 阈值区间对比

对 N=20000、50000 使用构图种子 `42、43、44、45、46`，分别定位平均 recall@10 达到 0.95、0.99 的最终 efsearch 区间。每个种子覆盖两个规模，各自独立构图，共十张索引、二十个目标。已有 seed=42、43 的结果核验后复用，只需补做 seed=44、45、46 对应的六张索引、十二个目标。

仅改变构图种子；base seed=42、query seed=45、1000 条查询、GT 及其余构图和搜索配置均沿用主实验。同一规模的 base/query/GT 哈希及实验二进制必须一致，记录实际构图种子、索引哈希和 campaign 来源，不覆盖历史结果。

阈值定位沿用主实验的按需括区间、整数二分和中点实测流程，20K、50K 均以 `R-L<=4` 停止。最终区间满足 `recall(L)<目标<=recall(R)`；保留原区间和中点，中点未达标也不改取 R。只运行定位阈值所需的点，不要求统一预算补点、同预算 recall 对照、完整曲线扫描或跨种子统计。

最终按规模和目标并列展示五个种子的 `(L,R]`、端点 recall、区间宽度及中点估计，比较区间重叠与位置变化即可。中点实测 recall 和是否达标一并保留作证据，不将区间估计称为精确最小阈值，也不据五组结果宣称普遍稳定或统计显著。
